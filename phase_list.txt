======================================================================
1. PROJECT OVERVIEW
======================================================================

1.1 What the platform does
- Investors track stock portfolios and holdings.
- The system stores daily stock prices (OHLCV) for every ticker.
- Every holding receives two machine-learning outputs:
  - Risk label: low, medium or high (Random Forest, checked against a Logistic Regression baseline).
  - Next-trading-day direction: up or down (Gradient Boosting, checked against "always up" and "same as today" baselines).
- Admins upload the price dataset and train the models from Django web pages.
- Every feature for investors and analysts is available through a JWT-secured REST API.
- Live risk monitoring through one WebSocket connection:
  - Live prices for the tickers a user follows.
  - An alert when a holding's risk label changes.
  - A notice when a requested recompute finishes.
- The REST API and the WebSocket are used by a Flutter app to test the project on a phone, emulator or browser.

1.2 Live risk monitoring — how to describe the project
- Objective: tell investors how risky each holding is and which way it is likely to move next, and push changes to their phone as they happen instead of making them refresh.
- The ML models do the slow thinking:
  - They use daily prices, run every night and after training, and give each holding a risk label and a next-day direction.
- The WebSocket delivers what changes in between:
  - Live portfolio value from live prices.
  - Risk-change alerts (for example medium to high).
  - Recompute results without polling.
- What the WebSocket does NOT do:
  - It does not stream predictions. A price change during the day does not change tomorrow's prediction until the next daily run.
  - Live prices come from Yahoo Finance every 2 minutes during market hours. This is near-live, not tick-by-tick.

1.3 Clients
- Flutter app (primary test client):
  - Used by investors, analysts and admins.
  - Talks to the /api/ endpoints with JWT tokens.
  - Opens one WebSocket to /ws/live/ with the same access token.
- Django web pages (session login):
  - Same role-based dashboards, portfolios and holdings.
  - Admin-only pages for dataset upload and model training.
- Postman collection:
  - Runs the full REST workflow automatically.
  - Prepares WebSocket URLs and triggers live events (WebSocket requests themselves are opened by hand in Postman).

1.4 User roles
- Investor:
  - Created by public registration (the only role registration can create).
  - Manages their own portfolios and holdings.
  - Sees their own prices, risk labels, forecasts and dashboard.
  - Receives live alerts for their own holdings.
- Analyst:
  - A registered user whose role an admin changed to analyst.
  - Read-only access to the portfolios of investors assigned to them.
  - Can queue price refreshes and prediction recomputes.
  - Receives live alerts for their assigned investors' holdings.
- Admin:
  - Created with createsuperuser, or promoted by another admin.
  - Sees everything and receives live alerts for every holding.
  - Manages roles and analyst assignments.
  - Uploads datasets and trains models.

1.5 Django apps
- accounts:
  - Custom User model.
  - Registration, login, JWT access and refresh tokens, logout blacklist.
  - Profile, change password.
  - Role management and analyst assignment.
  - Web login, register, profile and user management pages.
- core:
  - Shared code: ApplicationLogger, @log_execution_time, @admin_required, api_response helper.
  - Permissions, pagination, exception handler, throttles.
  - Cache keys and invalidation, MultipleFileField, Celery ping task.
- market_data:
  - PriceHistory and DatasetUpload models.
  - Dataset upload pages (CSV files, folder or zip) and the Celery import task.
  - Yahoo Finance provider (daily history and live quote) and daily price tasks.
  - Price APIs.
- portfolios:
  - Portfolio and Holding models.
  - Role-scoped CRUD APIs.
  - Portfolio summary.
- ml_training:
  - algorithms.py, feature_engineering.py, labels.py, dataset.py, train_risk.py, train_forecast.py, registry.py.
  - TrainingRun model, training tasks.
  - Admin training and model version pages.
- analytics:
  - Uses the trained models.
  - Prediction tasks, risk and forecast APIs, portfolio risk summary.
- dashboards:
  - Investor, analyst and admin dashboards (API and web).
  - Holding price trend.
  - Portfolio and holding web pages.
- monitoring (new in Phase 10B):
  - WebSocket consumer and routing.
  - Event publishing (price.update, risk.changed, prediction.updated).
  - Live price task.
  - No models and no tables.

1.6 Database tables
- users: custom User with role and the self-referencing assigned_analyst.
- portfolios: owned by one user.
- holdings: belong to one portfolio, carry the ML output fields.
- price_history: shared daily prices, unique on (ticker, date), joined to holdings by ticker.
- dataset_uploads: one row per dataset upload, with status, progress and per-file results.
- training_runs: one row per training run, with status, current step, new versions and results.
- Live prices are not a table. They are kept in the Redis cache for 24 hours so price_history only ever holds finished trading days.

2. STANDING DEVELOPMENT RULES
======================================================================

- Function-based views only for REST and web views.
- Exception (agreed): the WebSocket consumer is a class, because Django Channels only supports class-based consumers. It stays small: connect, disconnect, receive and one event handler.
- PyJWT for tokens, not SimpleJWT.
- Beginner-friendly code with no comments.
- Django forms / ModelForms for validation (WebSocket messages included), DRF serializers only for output.
- Every API response uses the status / message / data / errors format. WebSocket events use the same four keys plus type.
- settings.py stays a single file.
- Only add code or settings that are actually required, and explain why each one is needed.
- Update the Postman collection every phase.
- Deliver zips with only the changed files, and list any files to delete.
- Claude runs makemigrations, migrate and the tests; tests.py files are not delivered.

5. PHASE 10B — LIVE RISK MONITORING WEBSOCKET API (BACKEND)
======================================================================

Goal: one authenticated WebSocket per app that pushes live prices, risk-change alerts and finished recomputes, scoped by role, without changing any REST endpoint.

5.1 Packages and server
- channels: WebSocket routing and consumers.
- channels-redis: the channel layer that lets Celery workers send events to open connections.
- daphne: the ASGI server. Listed first in INSTALLED_APPS so "python manage.py runserver" serves HTTP and WebSocket together.
- No change to how the project is started.

5.2 Settings
- INSTALLED_APPS: "daphne" first, "monitoring" added. ("channels" is not required in INSTALLED_APPS.)
- ASGI_APPLICATION = "stock_risk_engine.asgi.application".
- CHANNEL_LAYER_REDIS_URL from .env (Redis database 4), added to the "all Redis URLs must differ" check (now five URLs).
- CHANNEL_LAYERS uses RedisChannelLayer with socket_timeout 10:
  - Why: redis-py 8 times out reads after 5 seconds by default, and the channel layer waits up to 5 seconds for messages. Without a longer timeout, any connection idle for about 5 seconds crashes with error 1011.
- Beat schedule: monitoring.tasks.poll_live_prices every 2 minutes, Monday to Friday, 13:00–21:58 UTC (covers US market hours in both summer and winter time).

5.3 asgi.py
- ProtocolTypeRouter: "http" goes to Django, "websocket" goes to the monitoring routes.
- No AllowedHostsOriginValidator:
  - Flutter on Android and iOS sends no Origin header, and that validator rejects connections without one.
  - The socket is authenticated with a token in the URL, not a cookie, so another website cannot use the user's session (the attack the Origin check prevents).

5.4 Endpoint and authentication
- URL: ws://<host>:8000/ws/live/?token=<access token>
  - Emulator: ws://10.0.2.2:8000/ws/live/?token=...
  - Phone: ws://<computer IP>:8000/ws/live/?token=...
  - iOS simulator and Flutter web: ws://127.0.0.1:8000/ws/live/?token=...
- The token goes in the URL because browsers cannot set an Authorization header on a WebSocket. Daphne logs only the path, never the token.
- The same checks as REST: valid signature, token_type access, active user, issued after the last password change.
- On failure: an "error" event, then close code 4401. Flutter refreshes the token and reconnects.

5.5 Messages from the app (validated by LiveActionForm)
- {"action": "subscribe", "tickers": ["AAPL", "MSFT"]}
- {"action": "unsubscribe", "tickers": ["MSFT"]}
- {"action": "ping"}
- Rules:
  - Tickers use the same pattern as the REST API and are upper-cased.
  - At most 20 tickers per connection.
  - Invalid JSON or an invalid message returns an "error" event with field errors; the connection stays open.

5.6 Events from the server
- Format: type + status + message + data + errors.
- connection.ready: user_id, username, role, token_expires_at, max_tickers.
- subscribed / unsubscribed: the tickers now followed.
- price.update: ticker, price, previous_close, change, change_percent, date, as_of, source (live or daily). Decimals are strings.
  - Sent on subscribe (latest known price), by the live price task, and after daily price downloads and refreshes.
- risk.changed: holding fields plus previous_label. Sent only when the label actually changes.
- prediction.updated: holding fields plus the task_id returned by the recompute API. Replaces task polling.
- pong: server_time and token_expires_at.
- error: errors explains the problem.

5.7 Who receives what (groups)
- user_<id>: every connection joins its own group.
- admins: admin connections also join this group.
- ticker_<TICKER>: joined on subscribe.
- Holding events go to the owner, the owner's assigned analyst and the admins group.
- Recipients are worked out when the event is sent, so reassigning an analyst takes effect immediately.

5.8 Session rules
- Token expiry is checked on every message and every event; an expired token closes the socket with 4401.
- Each ping re-checks the account in the database. A password change, deactivation or role change closes the socket with 4401.
- Flutter pings every 30 seconds and reconnects with a growing delay (1, 2, 4 … 30 seconds).

5.9 Live prices
- monitoring.tasks.poll_live_prices reads the latest price of every ticker held in a portfolio (yfinance fast_info: last_price and previous_close).
- Quotes are cached in Redis for 24 hours (key live_quote:<ticker>) and sent to ticker_<TICKER>.
- They are not saved to price_history: the daily table and the ML features only use finished trading days.

5.10 Files (Phase 10B delivery)

6. PHASE 11 — FLUTTER TEST CLIENT (REST + LIVE)
======================================================================

Goal: a simple, clean Flutter app that exercises every investor and analyst feature and the admin dashboards, with live prices and risk alerts, designed for phones first.

6.1 Project setup
- Separate repository, for example stock_risk_engine_flutter.
- Packages:
  - dio: HTTP requests and interceptors.
  - web_socket_channel: the live connection.
  - flutter_secure_storage: store access and refresh tokens.
  - provider: app state (logged-in user, role, live connection state).
  - go_router: navigation and role-based redirects.
  - fl_chart: price charts.
  - intl: number, currency and date formatting.
- Base URL passed at run time:
  - flutter run --dart-define=API_BASE_URL=http://10.0.2.2:8000
  - The WebSocket URL is derived from it: http -> ws, plus /ws/live/?token=<access>.
- Android debug builds: android:usesCleartextTraffic="true" so plain HTTP and WS work during testing.

6.2 Suggested folder structure
- lib/main.dart
- lib/config/api_config.dart (base URL and WebSocket URL)
- lib/core/api_client.dart (dio, interceptors)
- lib/core/token_storage.dart
- lib/core/api_response.dart (status, message, data, errors)
- lib/core/live_socket.dart (connect, ping, reconnect, event stream)
- lib/models/ (user, portfolio, holding, price, dashboard, risk, forecast, live_event, live_quote)
- lib/services/ (auth, portfolio, holding, market, analytics, dashboard, users)
- lib/screens/common/, lib/screens/investor/, lib/screens/analyst/, lib/screens/admin/
- lib/widgets/ (risk badge, direction badge, stat card, money text, live price chip, connection indicator, alert banner, error view, empty view, loading view)

6.3 Authentication and session
- Login screen accepts username or email and password.
- Save both tokens in flutter_secure_storage.
- Read user.role from the login response and open the matching home screen.
- Attach Authorization: Bearer <access> to every request.
- On 401: call /api/accounts/token/refresh/ once, save the new access token and retry; if refresh fails, clear tokens and go to Login.
- Logout: POST /api/accounts/logout/ with the refresh token, close the live socket, clear storage and go to Login.
- After change password, save the new token pair from the response and reconnect the live socket.

6.4 Live connection
- Open after login or splash; close on logout.
- Send ping every 30 seconds.
- On close code 4401: refresh the access token once and reconnect; if refresh fails, log out.
- On any other drop: reconnect after 1, 2, 4, 8, 16, then every 30 seconds.
- After reconnecting, subscribe again to the tickers on screen.
- Expose connection state (connected, reconnecting, offline) to the UI.

6.5 Screens — common
- Splash: check stored tokens, call /api/accounts/me/, route by role, open the live socket.
- Login: POST /api/accounts/login/.
- Register: POST /api/accounts/register/ (creates an investor).
- Profile: GET and PATCH /api/accounts/me/.
- Change password: POST /api/accounts/change-password/.

6.6 Screens — investor

  - Total value updates live from price.update for held tickers.
  - Risk-change alert banner from risk.changed.
- Portfolio list: GET /api/portfolios/ with pull-to-refresh and paging.
- Create / edit portfolio form: POST /api/portfolios/, PATCH /api/portfolios/{id}/.
- Delete portfolio with confirmation: DELETE /api/portfolios/{id}/.
- Portfolio detail:
  - GET /api/portfolios/{id}/summary/
  - GET /api/analytics/portfolio/{id}/risk-summary/
  - Subscribe to the portfolio's tickers; live value and day change per holding.
- Add / edit holding form: POST /api/portfolios/{id}/holdings/, PATCH /api/holdings/{id}/.
- Delete holding with confirmation: DELETE /api/holdings/{id}/.
- Holding detail:
  - GET /api/holdings/{id}/
  - GET /api/analytics/holdings/{id}/risk/
  - GET /api/analytics/holdings/{id}/forecast/
  - GET /api/dashboard/holdings/{id}/trend/ (line chart with buy price marker)
  - Live price chip with "Live" or "Daily close" from data.source.
- Stock lookup:
  - GET /api/market/prices/{ticker}/
  - GET /api/market/prices/{ticker}/history/
  - Follow button that subscribes to the ticker.

6.7 Screens — analyst
- Analyst home (dashboard): GET /api/dashboard/analyst/ (clients, high-risk holdings).
  - Live alert list from risk.changed for assigned clients.
- Client portfolios: GET /api/portfolios/ (only assigned investors), read-only.
- Portfolio detail and holding detail: same as investor but without add, edit or delete buttons.
- Actions on holding detail:
  - Recompute prediction: POST /api/analytics/holdings/{id}/recompute/, then wait for prediction.updated with the same task_id.
  - Fallback: if no event arrives within 30 seconds, poll /api/analytics/tasks/{task_id}/.
  - Refresh prices: POST /api/market/refresh/{ticker}/.

6.8 Screens — admin
- Admin home (dashboard): GET /api/dashboard/admin/ (user counts, totals, latest price date, models in use).
  - Live alert feed from risk.changed for all holdings.

- Edit user: PATCH /api/accounts/users/{id}/ to change role or assigned analyst.
- All portfolios: GET /api/portfolios/ (admin sees all).
- Datasets and ML Training:
  - Shown as an "Open in browser" link to /datasets/ and /ml/.
  - Uploads and training are done in the Django web pages.

6.9 Design rules for the Flutter pages
- Material 3, one seed colour, light and dark themes.
- Designed for phone width first; content stays readable on tablets and in Chrome.
- Bottom navigation per role:
  - Investor: Home, Portfolios, Stocks, Profile.
  - Analyst: Home, Clients, Profile.
  - Admin: Home, Users, Portfolios, Profile.
- The same colours as the web pages:
  - Risk: low green, medium amber, high red, not rated grey.
  - Direction: up green, down red.
  - Never colour alone: always show the label text too.
- Money shown with two decimals and a currency symbol; gains green with +, losses red with −.
- Every screen has loading, empty, error (with Retry) and success states.
- Pull-to-refresh on lists and dashboards; infinite scroll using the next link.
- Forms show the API's field errors under each field.
- Destructive actions ask for confirmation.
- ML outputs show the confidence and the model version, with the disclaimer that predictions are not financial advice.
- Read-only screens for analysts hide edit buttons instead of showing errors.
- Live rules:
  - A small connection indicator (connected, reconnecting, offline) in the app bar.
  - Live prices briefly highlight when they change; the label "Live" or "Daily close" is always shown.
  - Risk alerts show the old and new label as text, for example "AAPL: medium → high".
  - When offline, screens keep the last REST data and show "Live updates paused".

7. PHASE 12 — DEPLOYMENT (ASGI)
======================================================================

7.1 Containers
- Dockerfile for the Django app.
- docker-compose.yml services:
  - web: daphne -b 0.0.0.0 -p 8000 stock_risk_engine.asgi:application (serves HTTP and WebSocket)
  - worker: celery -A stock_risk_engine worker
  - beat: celery -A stock_risk_engine beat

  - redis: Redis (databases 0 to 4)
- Gunicorn is no longer needed for the web service, because Daphne serves both protocols.
- Shared volumes:
  - ml_models: written by the worker during training, read by the web app and worker.
  - media: written by the web app on upload, read by the worker during import.
  - postgres data volume.
- Health checks for db, redis and web.

7.2 Settings needed when the app is reachable from other machines
- DEBUG, ALLOWED_HOSTS and CORS origins read from .env instead of fixed values.
- STATIC_ROOT and collectstatic; static files served by WhiteNoise or a reverse proxy.
- HTTPS and WSS through a reverse proxy before any real users:
  - The proxy must pass the Upgrade and Connection headers for /ws/.
  - Turn off query-string logging for /ws/ in the proxy so tokens are not written to its access log.
- The Flutter release build uses the deployed https:// and wss:// URLs.
- Only needed if the project goes beyond local testing; local development keeps DEBUG = True.

7.3 Phase 12 acceptance checks
- docker compose up starts all five services.
- Upload, training and predictions work end to end in containers.
- WebSocket events from the worker reach the Flutter app through the proxy.
