======================================================================
1. PROJECT OVERVIEW
======================================================================

1.1 What the platform does
- The platform is a Django REST Framework backend for investors who want to track stock portfolios.
- Investors can create portfolios and add stock holdings to them.
- The system stores historical stock market data and retrieves current/latest prices.
- Each holding receives two machine-learning outputs:
  - Risk classification: Low, Medium, or High.
  - Next-trading-day direction prediction: Up or Down.
- The risk model is a Random Forest classifier.
- The direction model is a Gradient Boosting classifier.
- The system exposes functionality through JWT-secured REST API endpoints.
- The backend is intended to support a Flutter client in the future without requiring fundamental backend changes.

1.2 User roles and permissions
- Investor:
  - Creates and manages their own portfolios and holdings.
  - Views their own portfolio values, stock prices, risk labels, and forecasts.
  - Cannot access another investor's private portfolio data.
- Analyst:
  - Has read-only access to portfolios belonging to investors assigned to that analyst.
  - Assignment is represented by User.assigned_analyst.
  - Can trigger permitted market-price refreshes and ML recomputations.
  - Cannot create, edit, or delete investors' portfolios or holdings.
- Admin:
  - Can view all users, portfolios, holdings, and system-wide information.
  - Manages user roles and analyst assignments.
  - Has administrative access across the platform.

1.3 Main Django apps
- accounts:
  - Custom User model.
  - Registration and login.
  - JWT creation, refresh, logout, and refresh-token blacklist.
  - User profile management.
  - Role management and analyst assignment.
- core:
  - Shared permission classes.
  - Pagination.
  - Standard API exception handling.
  - API throttling.
  - Cache key and cache invalidation helpers.
- market_data:
  - Stores stock OHLCV price history.
  - Loads historical market data.
  - Fetches new market prices.
  - Provides latest-price and historical-price APIs.
- portfolios:
  - Stores portfolios and holdings.
  - Enforces investor, analyst, and admin access rules.
  - Provides portfolio CRUD, holding CRUD, and portfolio summaries.
- analytics:
  - Engineers ML features.
  - Trains and loads ML models.
  - Runs asynchronous prediction tasks.
  - Provides risk and forecast APIs.
  - Does not own a separate database table in the current plan; ML output fields are written onto Holding.

1.4 Main database relationships
- One User can own multiple Portfolios.
- One Portfolio can contain multiple Holdings.
- A Holding stores a ticker symbol, such as AAPL or MSFT.
- PriceHistory stores market data by ticker and trading date.
- Holding and PriceHistory are joined at query time using the ticker string.
- There is deliberately no foreign key from PriceHistory to Holding:
  - Market prices for a ticker are shared by every investor holding that ticker.
- User.assigned_analyst is a self-referencing foreign key:
  - It links an investor to the analyst responsible for that investor.
  - It is restricted to users whose role is Analyst.

1.5 Request and background-processing flows
- Normal synchronous API request:
  1. Client sends an HTTP request with a JWT.
  2. JWTAuthentication validates the access token.
  3. Permission classes check role-level and object-level access.
  4. The view processes the request.
  5. The serializer validates input or formats output.
  6. Django ORM reads or writes PostgreSQL.
  7. The response is returned to the client through the serializer.
  8. Heavy read endpoints, such as portfolio summaries, check Redis cache before querying the database.
- Background/asynchronous processing:
  1. Celery Beat triggers scheduled jobs.
  2. Jobs are placed on the Redis broker queue.
  3. A Celery worker executes the tasks.
  4. Tasks fetch market prices, recompute ML outputs, or retrain models.
  5. Results are saved to PostgreSQL through the Django ORM.
  6. Related Redis cache entries are invalidated.
  7. Celery task results are stored separately in Redis.

1.6 End-to-end user journey
- Investor registers and logs in.
- Login returns:
  - Access token valid for 15 minutes.
  - Refresh token valid for 7 days.
- Investor creates a portfolio.
- Investor adds a holding with ticker, quantity, buy price, and buy date.
- If recent price data for that ticker is unavailable:
  - The API queues a background price-ingestion task.
  - The API does not call the external market provider inside the request.
- Scheduled ML tasks calculate risk and forecast outputs for holdings with sufficient price history.
- The investor requests the portfolio summary.
- Redis returns a cached summary when a valid cached result exists; otherwise the API calculates it.
- The assigned analyst can view the same investor portfolio in read-only mode.
- When the access token expires, the client uses the refresh token to obtain a new access token.
- Logout blacklists the refresh token so it cannot be used again.

- Market Data is implemented before Portfolios, even though the source requirements PDF lists Portfolios first.

- Market Data depends on the Accounts app for authentication.
- Phase 5 (ML research and training) can run in parallel with Phase 4 (Portfolios), once Phase 3 price data is available.
- Phase 6 depends on both the completed Portfolio/Holding implementation and trained ML models.

5.1 Blocking defect 1A-1 — URL configuration is incorrect
- Current problem:
  - accounts/urls.py imports LoginView, MeView, and other API class views from views/views.py.
  - That module only defines function-based template views such as home_view, register_view, and others.
  - The URL list is duplicated.
  - Template pages are not routed correctly.
  - Templates using {% url 'accounts:...' %} can fail because the only configured namespace is api_accounts.
- Required fix:
  - Separate API URLs from web/template URLs.
  - Create accounts/urls/api_urls.py:
    - Set app_name = "api_accounts".
    - Register the API class-based views.
  - Create accounts/urls/web_urls.py:
    - Set app_name = "accounts".
    - Register the function-based template views.
    - Use route names: home, register, login, logout, dashboard, profile, user-list, and user-role-update.
  - Mount API URLs under api/accounts/.
  - Mount web URLs at the root.
  - Set LOGIN_URL to accounts:login.
  - Set LOGIN_REDIRECT_URL to accounts:dashboard.

5.2 Blocking defect 1A-2 — Refresh-token view crashes
- Current problem:
  - RefreshTokenView treats create_access_token(user) as if it returns a dictionary.
  - It attempts to access ["access"].
  - The function actually returns a token string.
- Required fix:
  - Assign the returned string directly:
    - access_token = create_access_token(user)
  - Return that string in the expected API response.

5.3 Blocking defect 1A-3 — JWT secret keys are empty
- Current problem:
  - .env contains empty JWT_SECRET_KEY and JWT_REFRESH_SECRET_KEY values.
  - os.getenv(name, SECRET_KEY) does not use the fallback when the environment variable exists but contains an empty string.
  - PyJWT 2.14 rejects an empty HMAC key.
  - Login therefore fails when token creation is attempted.
- Required fix:
  - Generate two different long random secrets using secrets.token_urlsafe(64).
  - Read each value using the equivalent of os.getenv(name) or SECRET_KEY so an empty string also falls back.
  - Ensure both JWT secrets are different from one another.
  - Ensure both JWT secrets are different from Django SECRET_KEY.
  - Refuse to start outside DEBUG mode if either JWT secret is empty.
  - Keep the secrets in environment configuration, not source control.

5.4 Blocking defect 1A-4 — Celery cannot start
- Current problems:
  - celery.py sets DJANGO_SETTINGS_MODULE to config.settings, which does not match the current settings package.
  - The logger import uses a relative path that goes beyond the top-level package.
  - stock_risk_engine/__init__.py does not load the Celery app.
  - The Celery app is named stock_tracker rather than stock_risk_engine.
- Required fix:
  - Point DJANGO_SETTINGS_MODULE to stock_risk_engine.settings, or to the appropriate settings module after the Phase 2 settings split.
  - Import ApplicationLogger using:
    - from config.application_logger import ApplicationLogger
  - Add the Celery app import to stock_risk_engine/__init__.py:
    - from .celery import app as celery_app
  - Rename the Celery app to stock_risk_engine.
  - Verify that celery -A stock_risk_engine worker starts.

5.5 Behaviour and security fixes
- 1A-5 — Prevent an admin from demoting themselves:
  - Current problem: the API permits an admin to change their own role.
  - Risk: the system could be left without an admin.

- 1A-11 — Keep role and staff status consistent:

  - Redis DB 2: application cache.

- Configure each Redis connection explicitly.

7. PHASE 3 — MARKET_DATA APP
======================================================================

Goal:
- Store, backfill, refresh, and serve ticker-level market data.
- Depends on Phase 2.

7.1 PriceHistory model
- Create a PriceHistory model with:
  - ticker:
    - CharField.
    - Store ticker symbols in uppercase.
    - Indexed for lookup.
  - date:
    - DateField.
    - Represents the trading date.
  - open_price:
    - DecimalField with 12 digits and 4 decimal places.
  - high_price:
    - DecimalField with 12 digits and 4 decimal places.
  - low_price:
    - DecimalField with 12 digits and 4 decimal places.
  - close_price:
    - DecimalField with 12 digits and 4 decimal places.
  - volume:
    - BigIntegerField.
    - BigInteger is required because some S&P 500 trading volumes exceed the 32-bit integer range.
- Add database constraints and indexes:
  - UniqueConstraint on ticker and date.
  - Index on ticker and date.
- The unique constraint makes ingestion idempotent and prevents duplicate ticker/date records.
- Do not create a foreign key from PriceHistory to Holding.
  - Price history is shared by all investors holding the same ticker.

7.2 Historical market-data backfill
- Dataset identified in the plan:
  - Kaggle dataset: "S&P 500 Stocks, Daily Historical Data (10 Years)".
  - One CSV file per ticker, for example AAPL.csv.
  - Expected historical period: 2015–2025.
- Create a management command:
  - python manage.py load_price_history <folder> [--tickers AAPL,MSFT]
- Command responsibilities:
  - Read CSV files using pandas.
  - Derive ticker from the CSV filename.
  - Rename source columns to the model's field names.
  - Remove invalid or malformed rows.
  - Insert rows using bulk_create.
  - Use batch_size=5000.
  - Use ignore_conflicts=True so rerunning the loader does not duplicate existing ticker/date records.
  - Log inserted/skipped counts per ticker.
- Verify the source CSV files contain Volume.
- The PDF's dataset description lists Date, Open, High, Low, and Close but does not explicitly list Volume.
- If Volume is unavailable:
  - Decide whether volume should be nullable, or
  - Remove volume-dependent features from the ML plan.
- Do not assume Volume exists until the downloaded files are inspected.

7.3 Live market-data provider
- The requirements PDF does not identify a live daily-price provider.
- Kaggle historical data ends in 2025, so a provider is needed for later dates.
- Candidate providers mentioned in the plan include yfinance and Alpha Vantage.
- Keep provider-specific code isolated:
  - Create market_data/services/provider.py.
  - Expose a consistent function that returns a pandas DataFrame.
  - Celery tasks should call this abstraction, not provider-specific code directly.
- This makes it possible to replace the provider without rewriting ingestion tasks.
- Final provider choice is an open decision (D1).

7.4 Celery tasks for market data
- fetch_daily_prices:
  - Scheduled through Celery Beat.
  - Runs daily after the US market closes.
  - Collects distinct tickers from existing Holdings plus any configured seed list.
  - Fetches dates later than the latest stored date for each ticker.
  - Inserts new price rows.
  - Invalidates portfolio summary caches affected by updated tickers.
- refresh_single_ticker:
  - Triggered by the market refresh API.
  - Also triggered when a new holding is added for a ticker without recent price data.
  - Retries with backoff when the provider fails.
  - Logs the ticker and error.
- External market-provider calls must not run synchronously inside an API request.

7.5 Market-data API endpoints
- GET /api/market/prices/{ticker}/
  - Access: any authenticated user.
  - Returns the latest stored price row for the ticker.
  - Returns 404 when no price row exists.
- GET /api/market/prices/{ticker}/history/
  - Access: any authenticated user.
  - Returns the ticker's OHLCV history.
  - Supports start and end date query parameters.
  - Results are paginated.
- POST /api/market/refresh/{ticker}/
  - Access: Analyst and Admin.
  - Queues refresh_single_ticker.
  - Returns HTTP 202 and a task_id.
  - Protected by per-user throttling.

7.6 Shared market-data selectors
- Create market_data/selectors.py.
- Implement latest_price(ticker):
  - Returns the latest price row for one ticker.
- Implement latest_prices(tickers):
  - Retrieves latest prices for multiple tickers in one query.
  - Returns a dictionary suitable for reuse by other apps.
- Portfolios and Analytics should reuse these selectors instead of implementing separate price lookups.

7.7 Phase 3 tests and completion criteria

- Unique ticker/date constraint is enforced.
- Latest-price endpoint returns the correct latest row.
- History endpoint returns correct rows.
- Date-range validation works.

9. PHASE 5 — ML RESEARCH AND MODEL TRAINING
======================================================================

Goal:
- Build, validate, and save the two ML models before connecting them to API serving.
- Depends on Phase 3, because historical PriceHistory data must be available.
- Can run in parallel with Phase 4.

9.1 Analytics code layout
- feature_engineering.py:
  - Builds model input features from historical price data.
- labels.py:
  - Creates target labels for risk classification and direction forecasting.
- training/train_risk.py:
  - Trains and evaluates the risk classifier.
- training/train_forecast.py:
  - Trains and evaluates the direction classifier.
- registry.py:
  - Loads the current model and its version.
- Store saved models as .joblib files.
- Keep model files in a git-ignored directory.
- Store a metadata JSON file next to each model.
- Use the existing @log_execution_time decorator around training functions.

9.2 Features to engineer
- Daily return.
- Rolling volatility over 30 trading days.
- Rolling volatility over 90 trading days.
- Maximum drawdown over a trailing window.
- 20-day moving average.
- 50-day moving average.
- Price-to-moving-average ratios.
- Relative Strength Index (RSI) over 14 periods.
- Volume trend, for example:
  - 20-day average volume divided by 90-day average volume.
- Holding-level features proposed in the requirements:
  - Holding age in days.
  - Unrealised gain/loss percentage.

9.3 Important training-data limitation
- Historical ticker price data does not contain investor-specific buy dates or buy prices.
- Therefore, it cannot directly provide the two proposed holding-level features for historical training rows.
- Decision D5 must be made:
  - Option 1: train using ticker-level features only, and calculate/show holding-level features alongside predictions at inference time.
  - Option 2: simulate buy dates and buy prices to create synthetic holding-level training examples.
- The implementation plan recommends Option 1 because it is simpler to explain and avoids introducing simulated holding data into model training.

9.4 Model 1 — Risk classifier
- Objective:
  - Classify a holding/ticker into Low, Medium, or High risk.
- Target creation:
  - Derive risk labels from future realised-volatility buckets.
  - Example approach: divide future realised volatility into three buckets using terciles.
  - Fix the future window and bucket thresholds for every model version.
- Main model:
  - RandomForestClassifier.
- Baseline model:
  - Scaled LogisticRegression.
- Output fields:
  - risk_label: predicted Low, Medium, or High class.
  - risk_score: probability associated with the predicted class.
- Evaluation:
  - Precision per class.
  - Recall per class.
  - F1-score per class.
  - Confusion matrix.
  - Saved feature importances.
- Compare Random Forest performance with the Logistic Regression baseline.
- If Random Forest does not outperform the baseline, document the result rather than hiding it.

9.5 Model 2 — Next-day direction forecaster
- Objective:
  - Predict whether the next trading day's closing price will be higher or lower than today's close.
- Target:
  - 1 when the next trading day's close is above today's close.
  - 0 otherwise.
- Model:
  - Gradient Boosting classifier.
- The requirements document is inconsistent about the library:
  - One section specifies scikit-learn.
  - Another mentions XGBoost or LightGBM.
- Recommendation in the implementation plan:
  - Start with scikit-learn HistGradientBoostingClassifier.
  - Add XGBoost only if testing demonstrates a measurable improvement.
- Output fields:
  - predicted_direction: Up or Down.
  - prediction_confidence: confidence/probability for the predicted direction.
- Evaluation:
  - Accuracy.
  - F1-score.
  - ROC-AUC.
  - Compare against simple baselines:
    - Always predict Up.
    - Repeat the previous day's direction.
- Set realistic expectations:
  - Around 50–55% accuracy can be normal for next-day stock-direction prediction.
  - Report results honestly; do not present accuracy alone as proof of a useful trading model.

9.6 Training and validation methodology
- Use chronological data splits only.
- Do not randomly shuffle time-series observations.
- Example split:
  - Training: 2015–2022.
  - Validation: 2023.
  - Testing: 2024–2025.
- Features for a given date must use only information available on or before that date.
- Avoid look-ahead leakage.
- Drop the first approximately 90 rows per ticker where rolling windows do not yet have enough history.
- Version models with descriptive identifiers, for example:
  - risk-rf-2026.10.14-01
- Save metadata containing:
  - Training window.
  - Feature list.
  - Label thresholds.
  - Evaluation metrics.
  - Model version.

9.7 Model training command
- Create:
  - python manage.py train_models
- Support:
  - --model risk
  - --model forecast
  - --model all
- The command should train the selected model or models and save model files and metrics metadata.

9.8 Phase 5 completion criteria
- Both models train from data stored in PostgreSQL.
- A metrics report is saved.
- Models can be loaded by version through the registry.
- Random Forest is compared with Logistic Regression.
- Direction forecasting is compared with the specified baselines.
- Any model that does not beat its baseline is documented accurately.
